## 一、代码库整体分析（Understand Knowledge Graph）

### 1.1 项目概况

**Causal Event Knowledge Graph (CEKG)**：从叙事文本（小说）中提取结构化因果知识图谱的 Python 流水线。

- 43 个分析文件（19 Python + 3 JSON + 3 Markdown + 18 小说文本）
- 88 个节点（34 file / 37 function / 8 class / 5 config / 4 document）
- 152 条边（36 imports / 52 contains / 39 calls / 5 documents 等）
- 流水线总代码量约 5,414 行 Python

### 1.2 架构六层

| 层 | 名称 | 核心职责 |
|---|---|---|
| A | 入口与编排 | CLI + CEKGPreprocessor 8 阶段串联 + checkpoint |
| B | 本体与配置 | schema.json 叙事本体论 + 事件/关系本体 + LLM 环境配置 |
| C | 数据模型与基础设施 | CEKEvent 等 dataclass + BoundedCache + DAGValidator + 断点续传 |
| D | 文本处理与事件抽取 | 章节分割 → LLM 事件抽取 → 指代消解 → RAG 段落索引 |
| E | 图谱构建与因果推理 | 上下文传播 → 候选对生成 → 反事实因果评估 → 通用图映射 |
| F | 主题标注与导出 | 五主题 LLM 标注 + Theme-Bridge 桥接 + JSON-LD/Cypher/CSV 导出 |

**数据流**：原始 .txt → [A] → [D] → [E] → [F] → JSON-LD / Neo4j / CSV，[B] 和 [C] 为全流程提供本体定义和类型系统支撑。

## 三、项目逻辑概述（5-10 句话）

CEKG 是一个从小说文本自动构建"谁做了什么、为什么、导致什么"因果知识图谱的流水线。先把小说按章节切开，逐段送 LLM 抽取出所有叙事事件（附原文引用、参与者、地点、时间），再用指代消解把"他""那个老人"等模糊称呼规整为统一角色名。接着沿事件序列传播时空上下文，补全 LLM 未提及的隐式信息，并通过嵌入相似度和 BM25 关键词筛选可能有因果关联的事件对（避免 O(N²) 全量配对）。候选对被送入 LLM 做反事实推理——"如果没有这个因，那个果还会发生吗"——只有通过反事实检验的才写入因果图。之后每个事件被标注对权力、财富、血缘、正义、认知五大结构主题的参与度，确定性规则自动沿因果链传播主题信息，构建主题子图。最终全套数据以 JSON-LD、Neo4j Cypher 和 13 文件 CSV 三种格式导出，支撑图数据库查询和 Web 可视化探索。整个流水线支持断点续传，且所有 LLM 调用带缓存去重，避免重复扣费。

## 四、示例：西游记全链路走通

用《西游记》"孙悟空被困五行山 → 唐僧收徒"的因果链。

### Stage 1: 章节分割

`text_processor.py` 用 5 种正则按"第X回"分割全书为 100 回。

### Stage 2: LLM 事件抽取

第七回和第十四回送 LLM，带 schema 本体约束，抽取结构化事件：

```
E1 大闹天宫:
  source_quote: "那大圣打上凌霄宝殿..."
  actors: ["孙悟空"], patients: ["天庭众仙"], place: "天宫"
  event_type: "@McKee CRISIS_DECISION"

E2 如来镇压:
  source_quote: "被佛祖翻掌一扑，将五指化作五行山压住"
  actors: ["如来佛"], patients: ["孙悟空"], place: "五行山"

E3 观音点化:
  actors: ["观音菩萨"], patients: ["唐僧"]
  why_factors: ["西天取经", "为悟空安排出路"]

E4 揭压帖:
  actors: ["唐僧"], patients: ["孙悟空"], place: "五行山顶"

E5 悟空破山:
  actors: ["孙悟空"]

E6 拜师:
  actors: ["孙悟空"], patients: ["唐僧"]
```

### Stage 3: 上下文传播

E4 原文没提地点。`propagate_context_attributes()` 发现前一个事件地点是"五行山"→ E4 自动继承地点="五行山"。Active entity propagation：E2 后活跃角色 {如来, 悟空}，E4 场景切换 → 如来自动淡出，活跃集合更新为 {唐僧, 悟空}。

### Stage 3.5: 指代消解

LLM 返回"那大圣""猴王""齐天大圣""行者""这猴子"→ `CoreferenceResolver` 全部规整为"孙悟空"。通过 KNOWN_WORK_ALIASES 种子 + 子串匹配 + 共现学习三层机制。

### Stage 6: 因果评估

候选对送 LLM 做反事实推理：

```
E1→E2: "如果没有大闹天宫，如来会镇压悟空吗？" → 不会 → DIRECT_CAUSE, 0.98
E2→E4: "如果没有镇压悟空，唐僧会去揭压帖吗？" → 不会 → DIRECT_CAUSE, 1.0
E3→E4: "如果没有观音点化，唐僧会揭压帖吗？" → 不会 → ENABLES, 0.90
E4→E5: "如果没有揭压帖，悟空能破山吗？" → 不会 → DIRECT_CAUSE, 1.0
E5→E6: "如果没有破山，悟空会拜师吗？" → 不会 → DIRECT_CAUSE, 0.95
```

DAGValidator (Kahn) 验证无环 ✓。最终因果链：E1→E2→E4→E5→E6（E3→E4 为额外入边）。

### Stage 7: 主题标注

LLM 逐事件标五主题：

| 事件 | POWER | KINSHIP | JUSTICE | KNOWLEDGE | WEALTH |
|------|-------|---------|---------|-----------|--------|
| E1 大闹天宫 | direcr+escalating | none | direct+challenging | indirect | none |
| E2 如来镇压 | direct+resolving | none | direct+resolving | none | none |
| E3 观音点化 | indirect+enabling | none | indirect+mediating | direct+initiating | none |
| E4 揭压帖 | indirect | none | direct+resolving | none | none |
| E5 破山而出 | direct+initiating | none | indirect | none | none |
| E6 拜师 | indirect+constraining | direct+initiating | none | indirect | none |

Theme-Bridge 传播：E1 有 POWER=direct → E2 自动升级 indirect+mediating → E4→E5→E6 连续获得 POWER=indirect。一条因果链只要有一个人 direct，整条链"通电"。

### 最终产出

```
exporters.py
├── JSON-LD: 语义网标准图
├── Neo4j Cypher: MERGE 幂等导入脚本
└── 13 CSV: 事件/agent/因果/主题/场景星型模型
```

## 五、深度技术问题七问

### Q1: 事件 JSON 片段的含义

```json
{
  "source_quote": "那大圣打上凌霄宝殿...偷桃盗丹，搅乱瑶池",
  "actors": ["孙悟空"],           // 主动执行者
  "patients": ["天庭众仙"],        // 被动承受者
  "place": "天宫",                // 地点
  "event_type": "@McKee CRISIS_DECISION"  // McKee 理论分类
}
```

`event_type` 受 schema.json 约束——不是自由标签，是从 62 种预定义类型里选的最匹配值。LLM prompt 内嵌受控词汇表，要求每个事件输出标准字段。`source_quote` 不在 LLM prompt 里，是 `_parse_event_json_data()` 根据 chunk 原文自动补的。

### Q2: 上下文传播（实体传播）的实现逻辑

**Pass1 — 地点/时间传播**（`graph_builder.py:12-37`）：

```python
current_location = None
for event in sorted_events:
    if event.location_context:       # 显式声明了地点？
        current_location = event.location_context   # 覆盖
    elif current_location:           # 没声明但前一个事件有地点？
        event.location_context = current_location   # 继承！
```

**Pass2 — 实体上下文传播**（`graph_builder.py:39-119`）：

```python
current_actors = {}
for event in sorted_events:
    if explicit_actors:             # 新角色登场？
        current_actors = explicit_actors   # 全量替换（旧角色退场）
    elif current_actors:            # 没新角色？
        for actor in current_actors:
            创建继承记录，strength=0.5  # 推断对，非显式
```

**过时角色删除**：当前代码**无 decay 机制**。注释写了"已从场景消失的角色在一定步数后淡出"，但实际实现是"有新角色就全量替换，没新角色就永远继承"。这是已知的技术债务。

### Q3: 指代消解的实现逻辑

五层策略依次尝试（`coreference_resolver.py`）：

1. **直接别名查表**：`alias_to_canonical` 字典，种子注入自 `KNOWN_WORK_ALIASES`
2. **子串/父串匹配**："Pip" in "Philip Pirrip" → 匹配
3. **首名匹配**："Joe" 的首词在 "Joe Gargery" 中出现 → 匹配
4. **首字母大写 = 真角色**：未匹配但首字母大写 ≤3 词 → 注册为新角色
5. **共现学习**：同事件中频繁共现的两个名字 → 自动建立别名

前置过滤：`is_valid_character_name()` 先滤掉代词（he/she/they/I）、通用描述词（"the man"/"someone"）、所有格开头。

**别名表维护**：`KNOWN_WORK_ALIASES` 手工维护 + 共现学习自动追加。重名冲突时后者覆盖前者（bug），生产级应报警。

### Q4: 实现逻辑为什么看起来像 Python 代码？真实逻辑是什么？

**两件事必须分开**：

| 类别 | 举例 | 实现方式 |
|------|------|---------|
| 确定性规则 | 上下文传播、别名查表、DAG 验证、Theme-Bridge 桥接 | 纯 Python（if-else, 字典查表, Kahn 算法） |
| LLM 语义判断 | 事件抽取、因果评估、Agent 分类、主题标注、场景分组 | LLM API 调用（prompt 注入本体约束） |

之前描述的实现逻辑确实是 Python 代码——因为它们真的是。但它们做的事是"结构化、验证、传播 LLM 的输出"，不是"替代 LLM 做语义判断"。整个架构的哲学：LLM 做它能做的（理解文本），代码做它擅长的（保证一致性）。

### Q5: 因果类型的完整列表和判断逻辑

**10 种超类型**：

| 超类型 | 含义 | 细粒度举例 |
|--------|------|-----------|
| CAUSAL_PRODUCTION | 因果产生 | DIRECT_CAUSE, TRIGGERS, ENABLES, FULFILLS |
| CAUSAL_CONSTRAINT | 因果阻碍 | PREVENTS, BLOCKS, COMPLICATES, MISSION_FAILURE |
| EMOTIONAL_DRIVE | 情感驱动 | EMOTIONAL_TRIGGER, EMOTIONAL_MANIPULATION, ENRAGES |
| SOCIAL_BOND | 社会纽带 | FAMILY_INFLUENCE, PERSUASION_ATTEMPT, INHERITED_OBLIGATION |
| NARRATIVE_ESCALATION | 叙事升级 | ESCALATES, MORAL_CHALLENGE, CAUSES_REVERSAL, PERSONAL_TRANSFORMATION |
| NARRATIVE_RESOLUTION | 叙事解决 | RESOLVES, REDEEMS, CONCLUDES |
| REVELATION_EPISTEMIC | 信息揭示 | REVEALS, EXPOSES, CONCEALS, FORESHADOWS |
| MEDIATION_TRANSFER | 中介传递 | TRANSFERS, DELEGATES, INFORMS, MEDIATES |
| THEMATIC_CONTRAST | 主题对比 | CONTRASTS, MIRRORS |
| THEMATIC_EXPLANATION | 主题解释 | EXPLAINS, SUPPORTS |

**LLM 选择逻辑**：prompt 要求"选择最具体的关系类型，不要在所有事件对上用同一个泛型"。优先级：EMOTIONAL_TRIGGER > MORAL_CHALLENGE > PERSONAL_TRANSFORMATION > REVEALS > ... > EVENT_ENABLES_NEXT > DIRECT_CAUSE。通过反事实测试的才判因果。DAGValidator 做 Kahn 拓扑排序确保无环。

### Q6: Agent 是什么？47 种类型

Agent = 叙事学中的"行动者"，**故事中执行动作或被动作影响的任何角色**。一个角色可同时是多种 Agent 类型，取决于具体事件中的叙事功能——是**每事件动态分类**而非固定标签。

47 种类型按功能分组：

| 功能组 | 类型 | 数量 |
|--------|------|------|
| 主角弧线 | PROTAGONIST_HERO, GHOST_BEARER, INNER_CRITIC, PSYCHOLOGICAL_MIRROR, PSYCHOLOGICAL_OPPONENT | 5 |
| 反派体系 | STRUCTURAL_ANTAGONIST, MORAL_ANTAGONIST, SHADOW_OPPONENT, INCITING_OPPONENT, EMOTIONAL_OPPONENT | 5 |
| 盟友体系 | MORAL_ALLY, PSYCHOLOGICAL_ALLY, REVERSAL_ALLY, FALSE_ALLY, STRUCTURAL_FOIL | 5 |
| 冲突升级 | ESCALATION_AGENT, CONFLICT_INTENSIFIER, STAKE_RAISER, PRESSURE_CATALYST, CRISIS_FORCER | 5 |
| 道德维度 | MORAL_CATALYST, MORAL_GUIDE, MORAL_PROVOKER, MORAL_REFLECTOR, MORAL_TEMPTER, MORAL_WITNESS, MORAL_BLOCKER, ETHICAL_CHALLENGER, CONSCIENCE_VOICE, VALUE_GUARDIAN | 10 |
| 情节引擎 | TURNING_POINT_DRIVER, PLOT_DISRUPTOR, PLOT_REVERSER, PLOT_BLOCKER, MOMENTUM_BREAKER, GAP_EXPANDER | 6 |
| 场景层面 | SCENE_CATALYST, SCENE_BLOCKER, SCENE_DIVIDER, SCENE_ESCALATOR | 4 |
| 知识/揭示 | REVELATION_GIVER, COMPASSION_TRIGGER | 2 |
| 冲突/解决 | OBSTACLE_AGENT, RIVAL, RESOLUTION_AGENT, ACT_BREAK_AGENT, CLIMAX_AGENT | 5 |

每个类型在 schema.json 中有对应的叙事学定义，LLM prompt 注入完整列表。

### Q7: 主题标注的完整实现逻辑（纯中文）

**Step 1 — 准备语境卡片**。为每个事件生成包含描述、参与者、因果邻域（谁导致的、导致了谁）的 JSON 卡片。

**Step 2 — LLM 标注**。把卡片发给 LLM，要求对 POWER/WEALTH/KINSHIP/JUSTICE/KNOWLEDGE 各输出三个值：参与程度（direct/indirect/latent/none）、叙事角色（7 种之一）、信心分（0-1）。并发数 20，超时 120s，两轮 + 兜底默认 none。

**Step 3 — 清理验证**。`_clean_theme_annotations()`：校验 LLM 输出的合法性，低信度降级（标 direct 但信心 <0.4 → 降 latent），缺失填充默认 none。

**Step 4 — Theme-Bridge 桥接传播**（最关键，纯确定性规则，零 API 调用）。逻辑：

```
对每个事件 E 和每个主题 T：
  如果 E[T].involvement == "none"：
    检查 E 的所有因果邻居（前驱和后续）：
      如果有邻居对 T 参与了 "direct"：
        E[T].involvement → "indirect"
        E[T].role → "mediating"
        E[T].confidence → min(0.6, 邻居conf × 0.6)
        E[T].evidence → "Bridge: linked to {邻居ID} via {因果类型}"
```

可传递——上游 direct → 下游 indirect → 再下游再 indirect → 整条链"通电"。

**Step 5 — 构建 THEMATIC 边**。`theme_graph.py` 纯规则：两事件对同一主题都 ≥indirect + 至少一方 direct + 信心都 ≥0.5 → 创建主题边。

## 六、CS/AI 技术视角的创新点总结

（以下分析剥离所有叙事学领域特有逻辑，仅从计算机科学和人工智能工程角度）

### 1. 受控词汇表 + LLM 联合推理（Ontology-Constrained LLM Generation）

每次 LLM 调用注入预定义受控词汇表，LLM 输出必须从枚举集合中选值。将开放域生成转为在预定义空间上的分类问题，消除输出不一致性。

### 2. 反事实因果推理 Prompt 工程（Counterfactual Causal Assessment）

Prompt 内置 Pearl 反事实测试范式——"如果原因事件没有发生，结果是否仍会发生？"强制 LLM 走反事实推理路径，大幅降低假阳性因果判定率。

### 3. 多头候选对生成（Multi-Strategy Candidate Pair Generation）

六种互补策略（邻接窗口、场景嵌入、双滑动窗口、BM25 关键词、实体引导、回退）筛选候选因果对，各策略独立打分后按 Tier 优先级合并去重上限截断。recall-precision trade-off 工程的典型案例。

### 4. 确定性规则覆盖 + 传播（Deterministic Rule Propagation on LLM Outputs）

Theme-Bridge 规则用纯图算法沿因果边传播主题标注——本质上是 **belief propagation on a causal DAG**。用确定性算法修复 LLM 标注的局部不一致，规则可传递。

### 5. 内容寻址缓存 + 断点续传（Content-Addressed Caching & Checkpoints）

SHA256 prompt 哈希缓存 + 阶段级 pickle 快照，使重跑边际成本趋近于零。

### 6. DAG 约束的 LLM 输出验证（Topological Sort as Guard）

Kahn 拓扑排序作门卫——LLM 输出通过图论约束过滤后才写入图，保证因果一致性。

### 7. RAG 增强的因果推理

段落级嵌入索引注入 LLM prompt，为跨章节因果评估提供叙事证据基座。RAG 模式在因果推理中的特殊应用。

### 8. 动态 Token 预算分配

按操作类型自动计算 max_tokens，避免截断和浪费。

### 一句话概括

**不是"把小说丢给 ChatGPT 收工"，而是把 LLM 当作带噪声的语义传感器，外围用图论、受控词汇表、确定性规则传播和缓存系统构建了一个鲁棒的知识抽取流水线。核心哲学：让 LLM 做它擅长的（理解文本），让算法做它擅长的（保持一致性）。这是一种 LLM-Native Software Architecture 的实践案例。**
