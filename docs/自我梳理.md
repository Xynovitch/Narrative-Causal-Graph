- 43 个分析文件（19 Python + 3 JSON + 3 Markdown + 18 小说文本）

## 三、项目逻辑概述

把小说按章节切开，逐段送 LLM 抽取出所有叙事事件（附原文引用、参与者、地点、时间）。用指代消解把"他""那个老人"等模糊称呼规整为统一角色名。沿事件序列传播时空上下文，补全 LLM 未提及的隐式信息。通过嵌入相似度、BM25 关键词、双滑动窗口等六种策略筛选候选因果对（避免 O(N²) 全量配对）。候选对送 LLM 做反事实推理——"如果没有这个因，那个果还会发生吗"——只有通过反事实检验的才写入因果图。每个事件被标注五大结构主题的参与度，确定性规则沿因果链传播主题信息。最终导出 JSON-LD、Neo4j Cypher 和 13 CSV。全流水线支持断点续传和缓存去重。

## 四、示例：西游记全链路走通

用"孙悟空被困五行山 → 唐僧收徒"的因果链走一遍。

### Stage 1: 章节分割

`text_processor.py` 用 5 种正则按"第X回"分割全书为 100 回。

### Stage 2: LLM 事件抽取

第七回和第十四回送 LLM，带 schema 本体约束，抽取结构化事件：

```
E1 大闹天宫: actors=["孙悟空"], patients=["天庭众仙"], place="天宫", event_type="@McKee CRISIS_DECISION"
E2 如来镇压: actors=["如来佛"], patients=["孙悟空"], place="五行山"
E3 观音点化: actors=["观音菩萨"], patients=["唐僧"]
E4 揭压帖:   actors=["唐僧"], patients=["孙悟空"], place="五行山顶"
E5 悟空破山: actors=["孙悟空"]
E6 拜师:     actors=["孙悟空"], patients=["唐僧"]
```

每个事件的 `event_type` 不是 LLM 自由发挥的——是从 `schema.json` 预定义的 62 种事件类型中选最匹配的一个。schema 就是一套"叙事学 ICD-10 编码"，LLM 输出时必须从这套受控词汇表里选，保证跨章节标签一致。

### Stage 3: 上下文传播

E4 原文没提地点。`propagate_context_attributes()` 按事件序列顺序遍历：当前事件没写地点 → 前一个事件有 → 继承。E4 自动获得 place="五行山"。

实体传播同理：维护一个活跃角色集合，新事件提到新角色就全量替换，没提到就继承——但当前代码**没有 decay 机制**，角色一旦进入活跃集合就永远在场，除非被新角色替换。注释里写了"淡出"但没实现。

### Stage 3.5: 指代消解

LLM 返回的角色名是"那大圣""猴王""齐天大圣""行者""这猴子"→ `CoreferenceResolver` 通过五层策略全部规整为"孙悟空"：直接别名查表（KNOWN_WORK_ALIASES 手工维护的种子）→ 子串匹配 → 首名匹配 → 首字母大写判断 → 共现学习。别名表手工维护，重名冲突时后者直接覆盖前者（这是 bug）。

### Stage 6: 因果评估

候选对送 LLM 做反事实推理。LLM 收到的 prompt 内置 Pearl 反事实测试范式——"如果原因事件没有发生，结果是否仍会发生？"只有通过反事实检验的才判为因果。同时 prompt 要求"选最具体的因果类型"，优先级从 EMOTIONAL_TRIGGER 到 DIRECT_CAUSE 逐级递减，避免 LLM 把所有事件对都标成同一个泛化类型。

```
E1→E2: DIRECT_CAUSE, 0.98
E2→E4: DIRECT_CAUSE, 1.0
E3→E4: ENABLES, 0.90
E4→E5: DIRECT_CAUSE, 1.0
E5→E6: DIRECT_CAUSE, 0.95
```

DAGValidator 用 Kahn 拓扑排序验证无环后才写入。

### Stage 7: 主题标注

LLM 逐事件标五主题（POWER/WEALTH/KINSHIP/JUSTICE/KNOWLEDGE）的参与程度、叙事角色和信心分。但 LLM 对单个事件的标注天然有局部不一致性——因果链上，上游事件标了 POWER=direct，下游可能标 POWER=latent（LLM 看不到全链视野）。

**Theme-Bridge 规则**就是解决这个的：纯确定性规则，不调 LLM。如果因果邻居对某主题有 direct 参与 → 当前事件自动升级为 indirect+mediating。规则可沿因果链传递——上游 direct → 下游 indirect → 下下游 indirect → 整条链"通电"。本质上是 **belief propagation on a causal DAG**。

最后 `theme_graph.py` 用纯规则构建 THEMATIC 边：两事件对同主题都 ≥indirect、至少一方 direct、信心 ≥0.5 → 创建主题边。

### 最终产出

JSON-LD、Neo4j Cypher、13 文件 CSV 三种格式。

## 五、基础知识：McKee 叙事理论和本体论

### McKee 理论

Robert McKee 是好莱坞剧本教练，《Story》（故事）是好莱坞编剧圣经。核心思想：故事是因果链条——每个场景包含"价值转折"（好变坏、坏变好），该转折由前一场景的事件必然导致。结构是：主角欲望 → 激励事件打破平衡 → 渐进危机 → 危机决策 → 高潮 → 解决。这套模型天然适合被形式化为带标签的有向图。

### 本体论

在这个项目里就是 `schema.json` 定义的受控词汇表：62 种事件类型、92 种因果关系、47 种角色类型、5 种主题。LLM 输出时必须从这套预设词汇里选，不能自由发挥。相当于为叙事分析做了一套 ICD-10 编码——把开放域生成转化为预定义枚举空间上的分类问题。

### Agent 的含义

Agent 是叙事学中的"行动者"——故事中执行动作或被动作影响的角色。一个角色在不同事件中可以是不同的 Agent 类型，不是固定标签。比如孙悟空在 E1 是 PROTAGONIST_HERO，在 E14 识别白骨精时是 REVELATION_GIVER。47 种类型定义在 schema.json 中，LLM prompt 注入完整列表。

## 六、深度技术逐层展开

### Q1: 上下文传播的真实实现逻辑

核心思想是维护"当前活跃状态"，新事件显式声明就覆盖，没声明就继承。Pass1 传播地点和时间，Pass2 传播演员和动机实体。当前代码的一个已知问题：**没有 decay（淡出）机制**。注释写了但没实现——角色一旦进入活跃集合，只有被新角色全量替换才会退场，不会因为"大段没出现"而自动淡出。这是在模拟读者认知（没提就是还在场），但没有处理"长期不提即退场"的边界情况。

### Q2: 指代消解的实现逻辑

五层策略：别名直查（KNOWN_WORK_ALIASES 种子）→ 子串匹配 → 首名匹配 → 首字母大写判断 → 共现学习。KNOWN_WORK_ALIASES 手工维护 + 共现学习自动追加。重名冲突时后者覆盖前者（bug），生产级需要检测一对多冲突并报警。

### Q3: Python 代码 vs LLM 判断——两者各司何职

这个项目最核心的架构哲学：LLM 做它能做的（理解文本语义），代码做它擅长的（保证结构一致性）。不要把"看起来像 Python 代码的描述"误解为"整个流程都是 Python 做的"——那些确实是 Python 代码，但它们做的是结构化、验证、传播 LLM 输出的工作，不是替代 LLM 做语义判断。LLM 负责事件抽取、因果评估、Agent 分类、主题标注、场景分组。确定性规则负责上下文传播、别名查表、DAG 验证、Theme-Bridge 桥接。两者互为补充。

### Q4: 别名表谁维护？重名冲突怎么办？

KNOWN_WORK_ALIASES 手工维护 + 共现学习自动追加。重名冲突时后者覆盖前者。以"那猴子"为例——如果先注册了"孙悟空 → ['那猴子']"，后来想注册"六耳猕猴 → ['那猴子']"，后者直接覆盖前者。但实际不会触发，因为手工维护的种子表不会分配冲突别名。生产级应该检测一对多冲突并报警。

### Q5: Theme-Bridge 桥接规则的完整逻辑

不调 LLM。纯确定性规则：如果因果边 A→B 存在，且 A 对某主题有 direct 参与，则 B 自动获得 indirect+mediating。规则可传递——一条因果链上只要有一个节点 direct，整条链下游全部"通电"。每个被升级的事件都记录了 evidence 字段，可以追溯"为什么标这个"。

## 七、双滑动窗口：算法设计与批判

### 算法本身

来自 `dynamic_context.py:142-192`。窗口大小 100 事件，步长 50，从头尾相向滑动：

```
轮 1: 左[0:100]   右[4900:5000]  → 距离 4800~4900
轮 2: 左[50:150]  右[4850:4950]  → 距离 4700~4800  
轮 3: 左[100:200] 右[4800:4900]  → 距离 4600~4700
...
轮 N: 左[2450:2550] 右[2450:2550]  → 左右相遇，距离 0~100
```

每轮对左右窗口内的事件做 100×100 嵌入相似度比较。复杂度 O(N × 100² / 50) ≈ O(N)。

### 设计意图

在 O(N) 复杂度约束下，给所有距离区间分配固定大小的"探测网格"。从最远距离开始往中间滑——因为最远的因果对（全书开头→全书结尾）往往是最重要的结构因果关系，先拿到它们。

### 批判：这个方案在逻辑上的缺陷

**1. 系统性漏掉某些距离带。** 窗口滑动的离散性导致某些事件对永远无法同时落入左右窗口。序列末尾 50 个事件（E4950-E4999）只能和开头 100 个事件（E0-E99）比较，和 E100-E4950 之间所有事件的比较全漏掉了。

**2. 对称性偏差没有理论支撑。** 从头尾向中间滑动的递减顺序（4800→4700→4600→...→0）来自机械操作，跟因果关系在距离上的真实分布没有任何关联。没有叙事理论说"距离 4800 的因果比距离 3800 的更值得先检测"。一个距离 2000 的关键因果对在第 50 轮才被扫到，前面 49 轮扫的远距离对可能全是噪音。

**3. 赌注没有支撑。** 算法设计者赌的是"跨章节因果必然有中间节点落到窗口里，所以通过传递性补齐"。但这个赌注没有实证支撑。如果两个远距离事件之间不存在中间媒介（直接的启动→后果关系），就真的漏了。

**4. 替代方案明显更优。** 分层随机抽样（按距离带分桶，每个桶均匀采样）在同等 O(N) 复杂度下消除了对称性偏差，每个距离带的覆盖概率均等。或者单窗口均匀滑动（不依赖双端对称），也能避免系统性盲区。

### 为什么还这样写

工程上的"先行动后求证"：O(N) 是唯一硬约束，双端滑动恰好是第一个能在这个约束下实现跨章节覆盖的方案。没有人做了因果距离分布的实证分析来决定采样策略——是先把复杂度降下来让系统能跑，然后根据真实产出的因果分布再调整。但这不改变设计本身在逻辑上缺乏正当性的事实。

## 八、七个深度技术问题的系统回答

### Q1: 事件 JSON 片段的含义

```
source_quote（原文引用）: "那大圣打上凌霄宝殿..."
actors（主动执行者）: ["孙悟空"]
patients（被动承受者）: ["天庭众仙"]
place: "天宫"
event_type（McKee 理论分类）: "CRISIS_DECISION"
```

`event_type` 受 schema 约束。LLM prompt 内嵌受控词汇表。`source_quote` 是代码根据 chunk 原文自动补的。

### Q2: 上下文传播的实现逻辑

Pass1 — 地点/时间传播：遍历事件 → 有就覆盖，没就继承。Pass2 — 实体上下文传播：活跃角色集合 → 新角色替换 → 没新角色就继承（strength=0.5）。无 decay 机制，已知技术债务。

### Q3: 指代消解的五层策略

别名直查 → 子串匹配 → 首名匹配 → 首字母大写判断 → 共现学习。前置过滤代词（he/she/it/I）、通用描述词（"the man""someone"）、所有格开头。

### Q4: Python 代码 vs LLM 判断

两件事分开：确定性规则（Python if-else、字典查表、Kahn 算法）处理已知事实；LLM 语义判断处理需要理解文本含义的事。架构哲学：LLM 当语义传感器，外围用图论和规则保证一致性。

### Q5: 因果类型的完整列表

10 种超类型：CAUSAL_PRODUCTION（产生）、CAUSAL_CONSTRAINT（阻碍）、EMOTIONAL_DRIVE（情感驱动）、SOCIAL_BOND（社会纽带）、NARRATIVE_ESCALATION（叙事升级）、NARRATIVE_RESOLUTION（叙事解决）、REVELATION_EPISTEMIC（信息揭示）、MEDIATION_TRANSFER（中介传递）、THEMATIC_CONTRAST（主题对比）、THEMATIC_EXPLANATION（主题解释）。LLM prompt 要求"选最具体的类型"，优先级从高到低，通过反事实测试的才判因果。DAGValidator 做 Kahn 验证。

### Q6: Agent 是什么？47 种类型

Agent = 叙事学中的"行动者"。每事件动态分类。47 种按功能分 9 组：主角弧线(5)、反派体系(5)、盟友体系(5)、冲突升级(5)、道德维度(10)、情节引擎(6)、场景层面(4)、知识/揭示(2)、冲突/解决(5)。

### Q7: 主题标注的完整逻辑

五步：准备语境卡片 → LLM 标注 → 清理验证 → Theme-Bridge 桥接（纯规则，belief propagation on DAG）→ 构建 THEMATIC 边（纯规则）。

## 九、CS/AI 技术视角的创新点总结

剥离叙事学领域特有逻辑，仅从计算机科学和人工智能工程角度。

### 1. 受控词汇表 + LLM 联合推理（Ontology-Constrained LLM Generation）

LLM 输出被限制在预定义枚举空间中，消除输出不一致性。将开放域生成转为分类问题。

### 2. 反事实因果推理 Prompt 工程

Prompt 内置 Pearl 反事实测试范式，强制 LLM 走因果推断路径，降低假阳性率。

### 3. 多头候选对生成

六种互补策略筛选候选对，各策略独立打分后 Tier 合并。Recall-precision trade-off 工程。

### 4. 确定性规则传播（Belief Propagation on Causal DAG）

Theme-Bridge 用纯图算法沿因果边传播主题标注，修复 LLM 局部不一致。可传递、零 API 调用。

### 5. 内容寻址缓存 + 断点续传

SHA256 prompt 哈希缓存，阶段级 pickle 快照。重跑边际成本 → 零。

### 6. DAG 约束的 LLM 输出验证

Kahn 拓扑排序作门卫过滤 LLM 输出，保证因果一致性。

### 7. RAG 增强的因果推理

段落嵌入索引注入 prompt，为跨章节因果评估提供叙事证据基座。

### 8. 动态 Token 预算分配

按操作类型自动计算 max_tokens。

### 一句话概括

**把 LLM 当作带噪声的语义传感器，外围用图论、受控词汇表、确定性规则传播和缓存系统构建鲁棒的知识抽取流水线。LLM 做它擅长的（理解文本），算法做它擅长的（保持一致性）。这是 LLM-Native Software Architecture 的实践案例。**

## 十、已知缺陷与技术债务

1. **上下文传播无 decay 机制**。注释写了"角色淡出"但未实现。长期不出现的角色永远在活跃集合中，直到被新角色替换。

2. **指代消解的重名冲突处理**。`alias_to_canonical` 字典存在时后者覆盖前者的问题。同一别名被映射到多个标准名时仅保留最后一次映射，且无报警。

3. **双滑动窗口的对称性偏差和距离带遗漏**。算法用机械的相向滑动顺序替代了因果距离分布的实际分析，存在系统性盲区。更好的替代方案（分层随机抽样、单窗口均匀滑动）未实施。

4. **场景策略的 per-scene cap 是硬编码的应急方案**。注释明确写了"防止密集场景吃掉全部预算压倒跨章节池子"——这个 30 的常数是对数据分布的过拟合，不是普适参数。

5. **OntologyManager 的 JSON 拼接修复逻辑**。`ontology_loader.py` 里有处理 schema.json 中多行字符串拼接的逻辑——说明 schema 文件本身存在格式问题，修复代码是 workaround 而非根因修正。
